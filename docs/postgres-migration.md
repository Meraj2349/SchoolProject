# Moving the backend from MySQL 8 to PostgreSQL 18

## Context
The school system is moving from MySQL to PostgreSQL. Research before the
move found that the hard part is not syntax but behaviour that changes
silently: identifier case folding, `SET` evaluation order, case-sensitive
comparisons, and how the driver returns dates and numbers. Every phase is
test-first so each of these is caught before production switches.

Decisions already made:
- **Names:** keep every table and column name and quote them (`"Students"."StudentID"`). API responses stay identical, so the website and the Flutter app don't change.
- **Legacy code:** port the SQL in place in `server/models` and `server/controllers`. Moving them into modules is not part of this work.
- **Hosting:** run `postgres:18` in docker-compose on the same server, with nightly `pg_dump` backups copied off the server.

Work happens on `feature/postgresql-migration`. MySQL stays in production until the cutover in Phase 6.

## Scale (from the code)
- ~32 server files use the db pool: legacy models and controllers plus 15 `src/modules/*/infrastructure/mysql-*.repository.js`.
- ~245 query calls. Some of them use features `pg` doesn't have, which must be rewritten by hand:
  - 34 `insertId` → `RETURNING`
  - 30 `affectedRows` → `rowCount`
  - 5 `IN (?)` with an array → `= ANY($1)`
  - 5 bulk `VALUES ?` → `unnest`
  - 6 `SET ?` with an object → explicit columns
- A few MySQL-only expressions: 4 `ON DUPLICATE KEY UPDATE`, 4 `CAST(... AS UNSIGNED)`, `IF()`, `FIELD()`, `NOW() - INTERVAL n MINUTE`, plus `ER_DUP_ENTRY` error-code checks.
- Schema: 39 tables, 22 ENUM columns, 16 `ON UPDATE CURRENT_TIMESTAMP` columns, 4 JSON columns. There are also 31 SQL files: `database.sql` plus 30 migrations.
- Tests: 27 integration test files touch SQL. 9 of them test old MySQL migrations against old schemas.

## Phases (each is test-first; one PR per phase or a few phases)

### Phase 0: Foundations, still on MySQL (no behaviour change)
1. **A db adapter in `server/config/db.js`** with this interface:
   - `query(sql, params)` returns `{ rows, rowCount }`
   - `one(sql, params)` returns the first row or `null`
   - `withTransaction(async (tx) => …)`
   - `isUniqueViolation(err)` and `isForeignKeyViolation(err)`

   First implement it on top of `mysql2`, then move every call site onto it. The result-shape changes (`[rows]`, `[[row]]`, `insertId`, `affectedRows`) and the error-code checks then happen once, while MySQL still runs and the existing tests prove nothing broke.
2. **Inserts.** Replace `insertId` with a helper `insertReturningId(table, row)` that hides `RETURNING` vs `insertId`.
3. **Driver-only parameter forms.** Rewrite `IN (?)`, `VALUES ?` and `SET ?` into explicit forms that work on both databases. Whitelisted column lists for `SET ?`.
4. **Node version.** Bump `server/Dockerfile` to `node:22-alpine` to match CI.

### Phase 1: The Postgres schema and migrations
1. **Hand-written schema** in `server/db/schema.sql`, with quoted original names:
   - identity columns (`GENERATED BY DEFAULT AS IDENTITY`)
   - `boolean`, `jsonb`, `numeric`
   - `timestamptz` for event times and `date` for `ClassDate`
   - ENUMs become `text` with a `CHECK`; unsigned columns get a `CHECK (... >= 0)`
   - one shared `set_updated_at()` trigger function and 16 triggers replacing `ON UPDATE CURRENT_TIMESTAMP`
   - `lower()` unique indexes where MySQL's case-insensitive collation enforced uniqueness (admin and teacher emails/logins)
   - the attendance day index from `attendance_day_index_migration.sql`
2. **Seed data** (branches, reference tables) in `server/db/seed.sql`.
3. **Migrations.** Adopt dbmate: numbered plain-SQL files in `server/db/migrations/` and a `schema_migrations` table. Migration 1 is the whole schema, squashing the 30 MySQL migrations. Update the "Schema changes" section of CLAUDE.md, since Postgres has native `IF NOT EXISTS` and transactional DDL.
4. **Test:** a schema test checks that the Postgres tables and columns match `database.sql`. It compares names, nullability and key columns using `information_schema` on both sides.

### Phase 2: The Postgres driver and dual-engine tests
1. **Postgres side of the adapter** on `pg` 8.x, with `DB_DIALECT=mysql|postgres`. Its jobs:
   - convert `?` placeholders to `$n` in one tested function (it must ignore `?` inside string literals)
   - type parsers for DATE (1082) to keep it a string, and for INT8 (20) and NUMERIC (1700) to return numbers where the current API returns numbers
   - set the session `TimeZone=Asia/Dhaka`
   - map `withTransaction` to `pool.connect()` + `BEGIN`/`COMMIT`/`ROLLBACK`
2. **Integration tests on Postgres:**
   - `globalSetup` builds from `server/db/schema.sql`
   - `resetDb()` becomes one `TRUNCATE ... RESTART IDENTITY CASCADE`, followed by `setval` after the fixed-id fixtures (branches 1 and 2, admins 9001–9003)
   - `insert()` uses `RETURNING`
3. **CI.** `.github/workflows/test.yml` runs the integration job as a matrix of `mysql:8` and `postgres:18`. The Postgres leg may fail at first: mark it `continue-on-error` until Phase 4 is done, then make it required.
4. **Old MySQL migration tests.** The 9 tests run only on the MySQL leg and are deleted at cutover.

### Phase 3: Port the risky SQL first, each with a test that pins the behaviour
- **Teacher-app login lockout.** `mysql-teacherAccount.repository.js` `reserveLoginAttempt` relies on MySQL's left-to-right `SET`. Rewrite it so it doesn't depend on assignment order, using a CTE or computed values. The test asserts lockout on exactly the Nth failed attempt.
- **Attendance save.** `mysql-attendance.repository.js` `saveDay` becomes `INSERT … ON CONFLICT ("StudentID","ClassDate") DO UPDATE … WHERE excluded."MarkedAt" >= "Attendance"."MarkedAt"`. Duplicate students in one payload are removed in the use case first. The existing "an older offline save never overwrites a newer correction" tests must pass on both databases.
- **Roll-number ordering.** `CAST(RollNumber AS UNSIGNED)`, used in 4 places, becomes a shared helper. On Postgres it is `NULLIF(regexp_replace(... , '\D', '', 'g'), '')::int`. Test it with a roll like `12A`.
- **Searches.** About 24 `LIKE` searches become `ILIKE` on Postgres through the adapter's `like()` helper, and email lookups use `lower()`. Tests check that mixed-case searches still find rows.
- **SMS.** The stale-"sending" recovery depends on `updated_at` advancing; it gets a test against the trigger.

### Phase 4: Port everything else, one module or legacy model at a time
- **The rewrites:**
  - quote identifiers
  - `IF()` → `CASE`
  - `FIELD()` → `array_position`
  - `ON DUPLICATE KEY` → `ON CONFLICT`
  - `NOW() - INTERVAL` → `now() - make_interval(...)`
  - `GROUP_CONCAT` → `string_agg`
- **Order:** fees, notifications, applications, quiz, content, gallery, dashboard, branch, admins, then the legacy `models/*`.
- **Done when** the full integration suite is green on the Postgres leg. Then make that leg required.

### Phase 5: Docker, mobile CI and operations
- **`docker-compose.yml`:**
  - a `postgres:18` service with a healthcheck and the volume at `/var/lib/postgresql`
  - a one-shot `migrate` service (`dbmate up`) that the backend waits on (`service_completed_successfully`)
  - keep a `mysql` service under a profile until rollback is no longer needed
- **Other files:** `.env.example` and `server/.env.example` get the new variables.
- **Mobile.** `.github/workflows/mobile.yml` and `mobile/teacher_app/tool/live_api_test.sh` run the live API on Postgres.
- **Backups.** A nightly `pg_dump -Fc` + `pg_dumpall --globals-only` script with retention, and documented restore steps.

### Phase 6: Data copy, rehearsal and cutover (runbook in `docs/postgres-cutover.md`)
1. **Copy script** `server/scripts/mysql-to-postgres/`: pgloader with `data only, reset sequences` into the Phase 1 schema. It uses a read-only MySQL user with `mysql_native_password`. A Node fallback copier exists in case pgloader cannot connect.
2. **Before copying,** check for zero dates and for duplicate emails that differ only in case.
3. **After copying:**
   - `setval` on every identity column
   - compare row counts and per-table hashes of normalised rows on both sides
   - run the smoke tests against the copied data
4. **Rehearse** on a copy of production and time it.
5. **Cutover.** Friday evening, API offline (teachers' phones queue attendance offline). Run the final copy and verify it, switch `DB_DIALECT`, run the smoke test, then reopen.
6. **Rollback.** Keep the MySQL volume and the last MySQL image untouched. Go/no-go is 48 hours after reopening; after that, delete the mysql2 path, the MySQL migration tests and the `mysql` compose service.

## Verification
- After every phase: `cd server && npm test` and `npm run test:integration` on MySQL. From Phase 2, also run them with `DB_DIALECT=postgres` against a local PostgreSQL 18 started in the container.
- `cd frontend && npm test` stays green, since the API shape doesn't change.
- Phase 5: `docker compose up` from empty volumes; log in, take attendance, check the fees page.
- Phase 6: a rehearsal copy with matching counts and hashes. Then the mobile `live_api_test.sh` against the copied database, and the full integration suite on the Postgres leg in CI.
